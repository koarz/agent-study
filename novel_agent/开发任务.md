  ## 第一阶段：文风系统

  这是下一步最应该做的功能。

  新增：

  python -m novel_agent style extract \
    --input "蛊真人全文错别字精校3.0.txt" \
    --output styles/冷峻谋略型.json

  然后支持：

  python -m novel_agent new ... \
    --style-profile styles/冷峻谋略型.json

  python -m novel_agent write PROJECT \
    --style-profile styles/冷峻谋略型.json

  python -m novel_agent polish PROJECT \
    --chapter 1 \
    --style-profile styles/冷峻谋略型.json

  文风画像应包含：

  - 平均句长和段落长度
  - 对白比例
  - 叙事视角
  - 动作、心理、环境描写比例
  - 节奏快慢
  - 信息揭示方式
  - 语言冷暖
  - 比喻和修辞密度
  - 解释程度
  - 章节结尾习惯
  - 冲突和悬念推进方式

  还要支持多个风格混合，例如：

  叙事节奏：冷峻谋略型 70%
  对白风格：自然口语型 30%
  描写风格：克制写实型 50%

  参考小说只提取抽象特征，不能把原文直接放进生成提示词或故事 RAG。

  ## 第二阶段：真正的长篇故事管理

  现在的故事圣经还偏静态，需要升级成动态故事系统。

  新增：

  - 卷、部、篇章、章节、场景四级结构
  - 每卷目标和核心冲突
  - 每个角色的阶段性成长路线
  - 角色当前知道什么、不知道什么
  - 角色关系变化
  - 物品和地点状态
  - 时间线
  - 未解决剧情线
  - 伏笔预计埋设、发展和回收节点
  - 生成过程中重新规划后续大纲

  也就是说，不能只保存“人物介绍”，还要保存：

  角色 A：
  知道的秘密：
  不知道的秘密：
  当前目标：
  当前情绪：
  与其他角色的关系：
  最近一次状态变化：

  这样才能支持几十万字甚至上百万字的长篇。

  ## 第三阶段：升级 RAG 为故事记忆系统

  现在主要是向量检索历史章节，后续需要分成几种记忆：

  1. 故事设定记忆
     世界规则、能力体系、历史背景。

  2. 结构化事实记忆
     谁在什么时候做了什么，谁知道什么。

  3. 章节正文记忆
     用来召回具体描写、对白和情节。

  4. 用户资料库
     用户上传的设定、资料、参考文档。

  5. 文风资料库
     只保存抽象文风画像，不和故事正文混用。

  后续检索应改为：

  关键词检索 + 向量检索 + 人物/事件过滤 + 时间线过滤 + 重排序

  这样才能避免：

  - 专有名词检索不到；
  - 数字和时间被忽略；
  - 召回未来章节；
  - 把其他项目的内容召回；
  - 只召回相似句子，却没有召回真正关键的事实。

  ## 第四阶段：增加更多创作模式

  现在主要是“生成下一章”，还需要支持：

  生成全书大纲
  生成某一卷大纲
  生成单章
  生成单个场景
  续写当前片段
  扩写
  缩写
  改写
  更换叙事视角
  更换时间顺序
  生成多个剧情分支
  生成不同结局
  只生成对白
  只生成动作戏
  只生成感情戏
  只生成悬念和伏笔

  例如：

  python -m novel_agent scene PROJECT \
    --chapter 12 \
    --prompt "只重写审讯场景，不能改变审讯结果"

  还要支持用户锁定条件：

  本章不能杀死主角
  不能新增角色
  不能改变伏笔 F03 的状态
  必须保留这句对白
  必须在结尾留下悬念

  ## 第五阶段：把审稿改成真正的编辑系统

  目前是整章审稿和整章润色，后续应增加：

  - 剧情审稿
  - 人物审稿
  - 时间线审稿
  - 世界观审稿
  - 伏笔审稿
  - 节奏审稿
  - 文风审稿
  - 对白审稿
  - 重复内容检测
  - 章节之间的相似度检测
  - 全书级逻辑审稿

  输出不应该只是“通过/不通过”，而应该类似编辑批注：

  第 12 章第 4 段：
  问题：角色在此处知道了一个此前尚未揭示的信息。
  建议：改为通过观察推测，不要直接确认。

  第 18 章：
  问题：伏笔 F03 预计在第 15 章回收，但目前仍未解释。
  建议：增加一次间接提示，或调整回收章节。

  润色也应支持：

  - 只采纳某一条建议；
  - 只改某一段；
  - 对比修改前后；
  - 一键撤销；
  - 改写后再次检查剧情是否变化。

  ## 第六阶段：版本和分支创作

  小说创作很需要回滚和试错，所以要增加：

  - 章节版本历史
  - 大纲版本历史
  - 人物版本历史
  - 分支剧情
  - 多个结局
  - 修改差异对比
  - 从某个章节复制新路线
  - 恢复到任意检查点

  例如：

  主线版本
    ├── 结局 A：主角牺牲
    ├── 结局 B：主角逃亡
    └── 结局 C：反转结局

  ## 第七阶段：作品包装和导出

  现在已有作品简介，后续还可以自动生成：

  - 一句话卖点
  - 长简介
  - 作者简介
  - 章节简介
  - 推荐语
  - 标签
  - 分类
  - 封面文案
  - 卷名
  - 目录
  - 内容警告
  - EPUB、TXT、Markdown、DOCX 导出

  这样才是从“写正文”变成“完成一部可发布作品”。

  ## 第八阶段：模型调度

  不同任务不应该永远使用同一个模型：

  - 小模型：人物状态提取、摘要、格式校验
  - 中等模型：章节规划、伏笔检查
  - 强模型：正文生成、关键场景改写
  - 独立审稿模型：逻辑和连续性检查
  - 本地模型：隐私内容和离线任务

  这样可以降低成本，也能提高稳定性。

  ## 最终功能形态

  完整版本应该形成这样的工作流：

  创意输入
    ↓
  题材与风格画像
    ↓
  世界观与故事圣经
    ↓
  人物关系和成长路线
    ↓
  卷纲、篇纲、章节纲
    ↓
  场景规划
    ↓
  正文生成
    ↓
  连续性检查
    ↓
  文风检查
    ↓
  局部修改
    ↓
  记忆和伏笔更新
    ↓
  全书审稿
    ↓
  简介、标签、排版和导出

  按功能开发量估计：

  - 文风提取和注入：约 3～7 天；
  - 动态故事记忆和长篇管理：约 2～4 周；
  - 多种生成模式和编辑审稿：约 2～4 周；
  - 版本分支、导出和创作界面：约 2～4 周；
  - 完整功能版大约 2～4 个月。
